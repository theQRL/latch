# Updating Latch

## Stronger option: keep the signer permanently offline

Install a current signed native app or PWA on a different device, verify it offline, and migrate the encrypted vault by QR. Do not reconnect the old signer. This avoids relying on logical deletion before reconnection.

## Maintenance on the same device

1. While both devices are offline, make a whole-vault QR backup from device A and restore it on B. Check every wallet address and test wallet-password access on B. A transfer receipt alone is insufficient.
2. On A, unlock Latch and open **Settings → Prepare this device for an update**. Acknowledge the tested backup and external-file handling, enter the vault passphrase, and type `WIPE THIS DEVICE`. Close all other Latch browser windows first.
3. Keep A offline until cleanup finishes and Latch reloads into **No vault stored**. An interrupted wipe resumes as **Finish clearing this device**, never as an updatable vault. Downloads outside Latch, OS backups and browser-managed credentials cannot all be erased by the app.
4. Reconnect the empty device. In the PWA, choose **Check for updates**, inspect the release identifier, and choose **Download and install**. Each asset is checked against its SHA-256 digest before the new cache is marked installed. Latch reloads into the new build when activation completes. Failure retains the old cache and empty maintenance state; retry or cancel a failed download once no worker is installing/waiting.
5. For native apps, close Latch and install a trusted signed package through the established distribution channel. Android requires the same app-signing identity. iOS uses its signed distribution mechanism. Latch itself does not download native code and Android still has no Internet permission. Production distribution is not configured in this review repository.
6. Disconnect A, reopen Latch, and select **Finish offline setup**. Cache verification and the absence of a pending PWA update are required. Restore the vault from B by QR, check addresses and wallet access again, and set up device unlock anew. Keep B intact until these checks pass.

Read [SECURITY.md](../SECURITY.md) before choosing same-device maintenance. Wipe means logical app cleanup, not guaranteed forensic erasure. The device also trusts new code when keys are restored later.

## Lifecycle

`sealed → wiping → maintenance → downloading → maintenance → sealed`

Native apps skip `downloading`; their signed package update occurs externally. A maintenance user can also finish offline setup without taking an update. Vault and settings writes require the original sealed generation. The PWA stores state and encrypted values in one IndexedDB transaction; native storage uses one serialized Preferences record. The service worker independently reads the same IndexedDB lifecycle before checking releases or installing candidates.

## Deployment

Deploy the complete, finalized PWA build on its dedicated HTTPS origin. Follow [Netlify deployment and verification](deployment.md); do not rewrite missing assets to HTML or alter generated bytes. Existing pinned installations use their cached release until the explicit maintenance workflow succeeds.

The static release metadata reports the build's content identifier. Its version pattern is currently `0.1.0+<12 hex characters>`; when changing the version scheme, update and test the release-ID validator in both page and worker. No signed release catalog or monotonic rollback protection is implemented. Browser-initiated worker checks cannot be disabled; candidate code must be trusted even when its install handler ultimately rejects installation.

PWA builds from before the maintenance implementation are deliberately pinned and cannot expose this new workflow. Adopt this version using a fresh installation/origin/device and verified migration. Do not clear a key-bearing installation just to get the new menu.

Keep encrypted recovery backups regardless of update mode. Test interruption, corrupt/missing assets, wrong release IDs, concurrent windows, storage failures and offline reopening before release. Native signing lifetime and upgrade persistence must be checked on real devices.
